# Mobile app (Android) — build & run

The Android app is a **Capacitor shell around the existing `public/` client**.
There is no second copy of the game: `mobile/scripts/sync-web.js` copies
`public/` into `mobile/www` and applies the transforms that a *bundled* client
needs. Change the game in `public/`, rebuild, and the app has it.

Why an app at all: it is the one anti-cheat measure that *prevents* rather than
detects. See `docs/ANTICHEAT_AND_CALIBRATION.md`.

> **Status: not yet built or run on a device.** All the code here was written and
> reviewed but never compiled — there is no JDK or Android SDK in the development
> environment. Treat the first `npm run build` as a debugging session, and see
> "What is most likely to break first" at the end.

## Layout

```
mobile/
├── capacitor.config.json      appId, webDir, androidScheme
├── .env.android.example       → copy to .env.android (gitignored)
├── scripts/
│   ├── sync-web.js            public/ → www/, with bundling transforms
│   └── apply-android-overlay.js   lays our native code over the generated project
├── native/android/            ← the native code WE own (tracked)
│   └── app/src/main/java/com/proofofsmart/quiz/
│       ├── MainActivity.java
│       ├── PlayIntegrityPlugin.kt
│       └── MobileWalletAdapterPlugin.kt
├── android/                   ← generated by `cap add android` (gitignored)
└── www/                       ← generated by sync-web.js (gitignored)
```

`android/` and `www/` are **build output**. Everything we wrote lives in
`native/` and `scripts/`, and the overlay script re-applies it after every sync,
so regenerating the Android project never loses our work. Every edit the overlay
makes is fenced with a marker and skipped if already present.

## One-time setup

1. **Install the toolchain**: JDK 17, Android Studio (SDK + platform tools).
2. **Configure the app**:
   ```bash
   cd mobile
   npm install
   cp .env.android.example .env.android   # then fill it in
   ```
   `GOOGLE_CLOUD_PROJECT_NUMBER` comes from Play Console → Play Integrity API. It
   is the project *number*, not the id. Left at `0` the plugin refuses to attest
   rather than producing a token the server cannot decode.
3. **Generate the Android project**:
   ```bash
   API_BASE=https://your-server npm run sync:web
   npm run add:android          # cap add android + overlay
   ```

## Build & run

```bash
cd mobile
npm run build            # sync + cap sync + overlay
npm run open:android     # then Run ▶ in Android Studio
```

`API_BASE` comes from `mobile/.env.android`, or from the environment for a
one-off (`API_BASE=https://other npm run build`). It is required and has no
default — the app has no same-origin server to fall back on, so a missing value
would produce a build that 404s every request.

It must be **HTTPS and reachable from the phone**. `androidScheme: https` plus
`allowMixedContent: false` means a plain-HTTP dev server is refused by the
WebView, and `localhost` is the phone itself. For local development, tunnel
(`cloudflared tunnel --url http://localhost:3000`) and put that URL in
`.env.android`; it changes on each tunnel restart, so re-run `npm run sync:web`.

Do not confuse it with `ALLOWED_ORIGINS` on the server, which must contain
**`https://localhost`** — the origin the app itself reports, not your server's
address.

## Server configuration

| Setting | Value | Why |
|---|---|---|
| `ALLOWED_ORIGINS` | add `https://localhost` | The app's pages load from the APK, so every request is cross-origin. Android reports the origin as `https://localhost`. Without this, every call fails with an opaque CORS error. The server warns at startup if attestation is on and this is missing. |
| `ATTESTATION_PROVIDER` | `google` | Default is `mock`, which trusts the client. **Refused outright in production** — a production deployment left on the default cannot attest anyone (rather than attesting everyone). |
| `GOOGLE_PLAY_INTEGRITY_CREDENTIALS` | service-account JSON | Inline or a path. |
| `ANDROID_PACKAGE_NAME` | `com.proofofsmart.quiz` | Checked against the verdict. |
| `ATTESTATION_REQUIRE_PLAY_RECOGNIZED` | `false` **for sideloaded betas** | A sideloaded APK reports `UNRECOGNIZED_VERSION` even on a healthy device. Set back to `true` once distributing through Play. |
| `STAKED_REQUIRES_ATTESTATION` | `false` until tested | The actual gate. Turn on only after a real device round-trips successfully. |

## What the bundling changes, and why

`server.js` does things at request time that do not happen for a file inside an
APK. `sync-web.js` compensates:

| Normally | In the app |
|---|---|
| Server injects `window.recaptchaEnabled` / site key | Written into generated `app-config.js` |
| Server sets the CSP header | `<meta http-equiv="Content-Security-Policy">`, including the API origin |
| `/socket.io/socket.io.js` served by the server | Rewritten to an absolute `API_BASE` URL |
| reCAPTCHA `<script>` | Stripped — see below |
| Relative `/api/...`, same origin | `public/net.js` rewrites to `API_BASE` |
| Session in an HttpOnly cookie | Bearer token (`Authorization` header + socket handshake) |

Admin, registration, subscription and tournament pages are **excluded from the
bundle**. Admin tooling should not ship in a player binary, and `subscription.js`
signs via the extension-only `signTransaction`, which MWA does not implement.

### reCAPTCHA

reCAPTCHA cannot run in the app: the page origin is `https://localhost`, which is
not a registered reCAPTCHA domain. The server **exempts sessions it has verified
as attested** (`socket/index.js`, using `isSessionAttested`). Play Integrity
answers the same "real human on a real device" question with a hardware-backed
signal, so this swaps a weak check for a stronger one rather than dropping a
defence. Note the exemption keys off *server-verified* attestation — a client
merely claiming `X-Client-Type: native` gets nothing.

### Wallets

No injected `window.solana` exists in a WebView, so Android uses **Mobile Wallet
Adapter**: the wallet is a separate installed app. Still non-custodial — we never
see a key.

`public/wallet.js` presents MWA as one more provider, so `game.js` and `login.js`
are unchanged. The one real difference is broadcasting: extensions sign locally
and let the page send; MWA signs *and* sends. `WalletManager.signAndSend()` hides
that, and the server only ever verifies an on-chain signature, so it cannot tell
the two apart.

Android 11+ hides installed apps unless declared — the overlay adds the
`<queries>` block for the `solana-wallet` scheme. Without it MWA reports "no
wallet found" on a phone with three installed.

## Verifying attestation end to end

1. Server with `ATTESTATION_PROVIDER=google`, credentials set,
   `STAKED_REQUIRES_ATTESTATION=false` at first.
2. Install and log in. Watch for `[ATTEST] Session attested for <wallet>`.
3. Confirm a `DeviceAttestation` row exists with a hashed `deviceId`.
4. Play a staked game from the app — it should behave exactly as the web does.
5. Only then set `STAKED_REQUIRES_ATTESTATION=true` and confirm the *web* client
   is refused with `NATIVE_CLIENT_REQUIRED` **before** any USDC moves.

Step 5's ordering is the one that matters: the gate runs ahead of stake
verification precisely so a refused client never pays and there is nothing to
refund.

## What is most likely to break first

Ranked by my confidence, lowest first:

1. **MWA API surface.** `MobileWalletAdapterPlugin.kt` is written against
   `clientlib-ktx` 2.0.x. That library has changed shape across versions
   (`transact` signatures, `TransactionResult` variants). Expect to adjust
   imports and result destructuring against whatever version resolves.
2. **`signAndSendTransactions` vs a partially-built transaction.** The stake
   transaction is built in `public/game.js` with a recent blockhash; if the
   wallet round-trip is slow the blockhash can expire. Web has the same risk but
   a shorter window.
3. **Gradle merge anchors.** The overlay patches `build.gradle` by matching
   `versionName` and `dependencies {`. If Capacitor's template changes, the
   script fails loudly rather than silently mis-patching — re-anchor it.
4. **Play Integrity project wiring.** The commonest failure is a project number
   that does not match the Play Console app; the server then cannot decode the
   token and reports `VERIFICATION_ERROR`.

## Distribution — choosing where the app is installed from

**Researched 2026-10-07.** Store policies change often; recheck the sources
below before acting on any of this. None of these routes replaces the legal
sign-off in `docs/MAINNET_LAUNCH_CHECKLIST.md` §0: they only decide whether a
*store* will carry the app, not whether staking is lawful where players are.

| | Google Play | Own website (APK download) | Solana dApp Store |
|---|---|---|---|
| Reach | Almost every Android phone | Any Android phone, but players must allow installs from your site | Solana Mobile phones only (Saga, Seeker: about 150,000 Seekers shipped) |
| Real-money staking | **Prohibited by default.** Allowed only as licensed gambling: an approved Google application, a licence per country, selected countries, Adults Only rating, age and geo-blocking | No store rules; only the law applies | **Not addressed** in the publisher policy or developer agreement. Apps that facilitate illegal activity are banned, and Solana Mobile can remove any app at any time without cause |
| Account / identity | Personal or organization. Licensed gambling realistically needs an **organization account** (registered company + D-U-N-S number) | Android developer verification (below) | Publisher portal account + **KYC/KYB** verification |
| Getting live | Personal accounts created after 13 Nov 2023: closed test with **12 testers for 14 days**, then a production review (about 7 days) | Immediate | Review in **3–5 business days**, live on approval |
| Cost | One-time registration fee | Hosting | **0% commission**; about 0.2 SOL for transaction and storage fees per submission |
| Updates | Automatic | **None automatic**: the app needs its own "new version" prompt | Through the store |
| Device check (Play Integrity) | Passes as Play-recognized | Fails "Play recognized" | Fails "Play recognized" |

**Android developer verification applies to every route.** Google now requires
apps installed on certified Android devices to come from a developer who has
registered their identity, whether the app comes from Google Play, another
store or a website. Registration opened in March 2026; enforcement began on
30 September 2026 in Brazil, Indonesia, Singapore and Thailand, and is planned
worldwide in 2027. Unverified apps can then only be installed through an
"advanced" flow or adb. Register before distributing by any route. (The Seeker
ships with Google Play, so dApp Store installs are very likely covered too.)

**Device-check setting for non-Play installs.** A copy installed from the
website or the dApp Store reports `UNRECOGNIZED_VERSION`. If staked play
requires attestation (`STAKED_REQUIRES_ATTESTATION=true`), those players could
not stake unless `ATTESTATION_REQUIRE_PLAY_RECOGNIZED=false` (see Server
configuration). That keeps the genuine-device check but drops the guarantee
that the app itself is unmodified, so pair it with a signed APK, a published
checksum, and the server-side cheating checks.

**Why the dApp Store fits this app.** Its users already hold Solana wallets, and
the Seeker's built-in wallet works through Mobile Wallet Adapter, which the app
already uses. It takes no commission and has no real-money-gaming ban. The
trade-offs: a small audience (Seeker owners only), removal at Solana Mobile's
discretion, and the publisher wallet must never be lost, because it is needed
for every future update of the app.

**A sensible order:** register for Android developer verification; publish to
the dApp Store and/or the website once legal sign-off covers the target
markets; treat Google Play as a free-play-only listing unless a gambling licence
and Google's approval are obtained.
